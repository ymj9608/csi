# 아키텍처 맥락을 이용한 반복 탐색 평가 계획

이 문서는 후속 공개 저장소 실험의 **실행 전 계획**입니다. 이미 측정한 합성/Lichu 결과를 수정하지 않습니다. 목표는 “그림을 읽으면 더 빠르다”를 전제하는 것이 아니라, **같은 보안 검증 품질을 유지하며 반복 탐색 비용을 줄이는 조건이 있는지** 확인하는 것입니다. 아래에 고정한 파일럿은 질의 1개·방식별 1회이며, 일반 평가 계획에서 설명하는 다수 질의 반복 실험을 완료한 것으로 간주하지 않습니다.

## 이번 파일럿에 고정한 조건

실행 전 고정한 실제 명세와 파일별 해시는 [petclinic-protocol.json](benchmarks/petclinic-protocol.json)을 기준으로 합니다. 이번 파일럿과 아래 일반 확장 계획이 다르면 JSON의 고정 조건을 따릅니다.

| 항목 | 고정값 |
| --- | --- |
| 공개 저장소 | `spring-petclinic/spring-petclinic-microservices` |
| 기준 커밋 | `1d76b00d683e86b62867a6bf59530f8ab301244f` |
| 범위 | 추적 Java/properties/sql/xml/yaml/yml 111개, 174,891 bytes; `.github/`, `.mvn/` 제외 |
| Java 구성 | 64개: 운영 코드 53개, 테스트 11개; Maven 모듈 8개 |
| 구조 그림 | 같은 커밋의 원본 `docs/microservices-architecture-diagram.jpg`; 정답 경로나 파일명을 추가하지 않음 |
| 질의 | 소유자 생성·수정에서 `telephone` 입력→저장·로그 경로를 검토하고 원문 근거·개선 계획 제시; 코드 수정 없음 |
| 초기 근거 | 스캐너가 발견했다는 동일 조건의 `OwnerResource.java` 한 파일과 `telephone` 필드; 두 번째 정답 경로는 입력하지 않음 |
| 방식 | 전체 111개 배치 / 코드 인덱스 선별 / 실제 저장된 비전 맥락 + 동일 코드 인덱스 선별 |
| 선별 예산 | 두 선별 방식 모두 최대 12개 파일·48,000 source bytes |
| 실행 | 동일 질의 방식별 1회, 순서 `full_batch → indexed_code → cached_vision_indexed`; 순서·캐시 영향은 한계로 공개 |
| 정답 분리 | 로그 관련 알려진 후보 2개와 전화번호 저장 경로는 평가자가 별도 관리; 정답 경로를 모델 프롬프트·검색 순위에 주입하지 않음 |
| 품질 조건 | 초기 스캐너 근거 유지, 알려진 후보의 추가 누락 없음, 실제 원문 인용과 저장 경로 근거 확인 |

전체 방식의 범위는 **저장소의 모든 파일**이 아니라 위 확장자·제외 규칙으로 고정한 백엔드·테스트·빌드/배포 구성입니다. 데이터베이스 종류는 실제 코드에 따라 설명하며 PostgreSQL로 가정하지 않습니다. 원본 그림이 새 서비스나 GenAI 경로를 누락했다면 그 자체를 실험 조건으로 남기고 모델이 잘 찾도록 그림을 고치지 않습니다.

이 파일럿의 캐시 재사용 단계는 실제 저장된 맥락을 읽어 실행합니다. 그러나 같은 저장소의 서로 다른 요청 N개를 실행한 것은 아니므로 N=5/10/20 비용 표는 작성하더라도 **실측 단계에 기반한 추정**으로 표시해야 합니다. 초기 이미지 분석·인덱스 생성 비용은 각각 공개합니다.

## 1. 실험 대상과 입력을 먼저 고정

후속 확장 실험은 모델 호출 전에 다음 항목을 별도 protocol JSON에 기록하고 SHA-256을 남깁니다. 이번 파일럿의 저장소·커밋·목록은 위 링크에 고정했습니다.

- 공개 저장소 URL·라이선스·고정 커밋, 허용 확장자·제외 목록·각 파일 해시. 실제 개인정보·비밀 값이 없는지 확인합니다. 의존성/vendor·빌드 결과·문서는 소스 범위와 분리합니다.
- 하나의 실제 저장소에서 고정 질의 목록을 정합니다. 예: “전화번호 입력에서 DB 저장과 외부 전송까지 확인하고, 원문 로그 여부를 근거와 함께 설명하라.” 저장·로그·비동기 작업·외부 전송을 각각 별도 목표로 나눠 질의당 기대 결과를 정의합니다. 단순 문자열 등장 횟수를 취약점 정답으로 삼지 않습니다.
- 명시적 필드명, DTO/직렬화 별칭, 공통 래퍼, 비동기 소비자 등 서로 다른 코드 경로를 포함합니다. 실험 후 잘 맞은 질의만 남기지 않습니다. 양성·음성 대조군과 그림에 없는 경로도 사전에 라벨링합니다.
- 정답에는 기대 동작, 근거 파일·행 범위, 호출·데이터 흐름, 정상 대조 이유를 기록합니다. 가능하면 기존 테스트 또는 작은 결정적 동작 검증으로 뒷받침합니다. 불확실한 항목은 점수 분모에서 제외하는 대신 제외 이유를 기록합니다.
- 그림의 출처·작성 시점·대상 커밋·해시를 기록합니다. 평가 정답을 보고 정답 경로만 그리지 않습니다. 사람이 새로 그렸다면 준비 시간과 참조 파일을 공개하고 “기존 운영 문서”로 소개하지 않습니다.
- 모델 태그·digest, Ollama/OS/하드웨어, runner·프롬프트·스키마 해시, 입력/출력 한도, seed·temperature, 시간 제한, 반복 횟수, 실패 처리와 arm 순서를 고정합니다.

정답 JSON·기대 경로·평가 스크립트·채점 결과는 모델 입력과 검색 인덱스에서 제외합니다. 파일명에 `vulnerable`처럼 정답을 드러내는 평가 전용 이름을 사용하지 않습니다. 실제 공개 코드에 그런 이름이 있다면 원문을 유지하고 편향으로 기록합니다.

## 2. 비교하는 세 방식

| 방식 | 질의 시 입력 및 동작 | 목적 |
| --- | --- | --- |
| `full_batch` | 범위 내 전체 코드를 번호 있는 배치로 읽고 질의별 결과를 합칩니다. 동일 질의·리뷰 프롬프트·모델을 사용합니다. | 저장소 전체를 매번 읽는 비용과 검증 품질 |
| `indexed_code` | manifest·심볼·지원하는 import/호출 관계 인덱스를 만든 뒤, 질의와 스캐너 근거로 관련 코드를 선택합니다. 이미지 맥락은 제공하지 않습니다. | 코드 검색 자체의 비용 절감 효과 |
| `cached_vision_indexed` | 같은 인덱스와 같은 검색 규칙에, 최초 1회 추출한 이미지 구성요소·흐름을 참고 맥락으로 더합니다. 질의마다 저장된 맥락을 실제로 읽습니다. | 코드 검색 대비 아키텍처 맥락의 추가 효용 |

`indexed_code`와 `cached_vision_indexed`의 인덱스 구현·버전·검색 후보 수·코드 토큰 예산·연관 경로 확장 규칙은 동일해야 합니다. 비전에만 사람이 정답 경로를 넣거나 더 큰 코드 예산을 주지 않습니다. 아키텍처 맥락의 추가 토큰도 비용에 포함합니다. 이미지에만 제공된 구조 정보를 동일한 텍스트로 주는 보조 실험이 없으면 **구조 정보의 이점과 비전 모델 자체의 이점을 분리해서 주장할 수 없습니다**.

`full_batch`는 단순히 전체 문자열을 한 번에 잘라 보내지 않습니다. manifest 범위의 모든 문자가 전달됐는지 확인하고, 배치 간 필요한 관계를 합치는 비용도 기록합니다. 세 방식 모두 실제 원문 근거를 요구하며 구조 그림만으로 위험을 확정하지 않습니다.

## 3. 선택 전에 적용하는 근거 보존 규칙

관련 코드 선별은 다음 순서를 따르며, 질의별 선택 로그에 각 파일이 포함된 이유를 남깁니다.

1. 공통 스캐너가 검사한 전체 범위, 현재 변경 파일, 질의에 직접 연결된 스캐너 근거 파일을 기록합니다. 보안 스캐너는 그림 때문에 범위를 줄이지 않습니다. 이 공통 비용은 한 번만 실행하더라도 실제 시간과 범위를 기록합니다.
2. 스캐너가 근거로 제시한 파일과 실제 변경된 위험 구간은 **필수 입력**입니다. 그림에 없거나 검색 점수가 낮다는 이유로 제거하지 않습니다. 필수 입력이 예산을 넘으면 분할·추가 호출 또는 전체 검토로 전환하며 비용에 포함합니다.
3. 선택적 후보는 manifest에 실재하는 경로·심볼로만 해결합니다. 이미지 텍스트나 모델 응답을 파일 접근 경로로 직접 사용하지 않습니다. 후보별 `scanner_anchor`, `changed_file`, `symbol_match`, `import_edge`, `architecture_component` 등 근거와 순위를 기록합니다.
4. 흐름의 실제 시작점·변환·저장/출력 지점 중 필요한 근거가 빠지면 추가 조회합니다. “전화번호”라는 문자열이 없다는 이유만으로 개인정보 흐름이 없다고 판단하지 않습니다. 별칭·래퍼·비동기 연결은 실제 지원되는 인덱스 범위만 주장합니다.
5. 다이어그램이 업무 흐름 그림이거나 커밋 불일치, 경로 불일치, 필수 근거 누락이면 아키텍처 기반 축소를 중단하고 코드 인덱스 또는 전체 배치로 넘어갑니다. 전환 조건을 실행 전에 고정하고 전환 빈도·추가 비용을 기록합니다.

이 규칙은 “전체 저장소를 비전으로 대체”하는 실험이 아닙니다. 전체 정적 검사 위에서 **LLM에 읽힐 코드의 순서와 범위를 조절**하는 실험입니다. 공통 스캐너가 놓치는 위험도 있으므로 그림 밖 보안 후보를 별도 정답으로 넣어 누락을 측정합니다.

## 4. 품질을 먼저 평가

다음 항목을 서로 분리해 질의별로 집계합니다.

- **후보 정확도:** 목표 동작의 경로·유형이 정답에 맞는 TP/FP/FN. 단순 전화번호 필드 존재나 그림의 DB 연결은 위험 확정 근거가 아닙니다.
- **원문 근거 정확도:** 인용이 실제로 제출한 코드의 정확한 파일·행에 존재하는지, 그 행이 주장한 동작을 지지하는지. 문자열 일치만으로 의미상 근거까지 맞다고 간주하지 않습니다.
- **흐름 설명 정확도:** 라벨링된 입력→변환→저장/로그/외부 전송 연결의 누락·허위 연결. 모르는 연결을 불확실성으로 표시했는지.
- **누락 안전성:** 필수 스캐너 파일 포함률, 그림 밖 라벨 위험의 재현율, 정상 대조군 오탐률. 질의 범위 밖 위험은 목표 질의 점수와 분리해 전체 안전성 보조 점수로 보고합니다.
- **완료율:** 정상 JSON·시간 제한·입력 한도·검증을 통과한 작업 수. 오류나 fallback을 성공 실행 통계에서 조용히 제거하지 않습니다.

파일 선택만 줄이고 정답 근거가 빠진 결과에는 “효율 개선” 표시를 붙이지 않습니다. 작은 파일럿의 기본 통과 조건은 **필수 근거 파일 100% 보존, 알려진 양성에 대해 비교 기준보다 추가 누락 없음, 근거가 검증된 TP 감소 없음**입니다. 추가 오탐이나 완료율 저하가 있으면 함께 보고하고 “품질 동등”이라고 주장하지 않습니다. 이 조건을 충족해도 통계적 비열등성을 입증한 것은 아닙니다.

## 5. 시간·토큰·캐시 비용

인덱스 생성과 이미지 분석을 각각 별도 단계로 계측합니다. 저장된 이미지 맥락을 파일/DB에서 다시 읽고 코드 선택·모델 호출·검증을 마칠 때까지의 실제 end-to-end latency를 기록합니다. 이전 실행에서 비전 시간만 뺀 값을 실제 캐시 요청 측정값으로 대신하지 않습니다.

| 비용 | 반드시 포함할 항목 |
| --- | --- |
| 최초 준비 | 공통 manifest/인덱스 생성, 이미지 분석, 맥락 저장; 그림 수동 작성은 별도 인력 비용 |
| 질의별 | 맥락/인덱스 읽기, 후보 검색·확장, 전체 또는 선택 코드 추론, 추가 조회·fallback, 결과 검증 |
| 갱신 | 커밋별 인덱스 갱신, 이미지/모델/프롬프트 변경 시 비전 재실행 |

각 모델 호출의 실제 `prompt_eval_count`, `eval_count`, 제공되는 경우 `prompt_eval_cached_count`, 모델 로드·prefill·생성 시간, 클라이언트 wall time을 저장합니다. 바이트 수를 토큰 수로 바꾸어 실측처럼 쓰지 않습니다. 이미지 토큰을 제공자가 따로 보고하지 않으면 분리 추정값으로 표시하지 않습니다. cache count가 없는 응답은 0으로 단정하지 않습니다.

반복 질의가 N개인 실제 측정 구간의 총비용은 `최초 준비 비용 + N개 질의 비용 + 해당 구간의 갱신 비용`입니다. `N=1, 5, 10, 20` 등 실행 전에 정한 구간을 보고하되 실제로 수행하지 않은 N은 추정으로 구분합니다. 비전 방식의 질의당 비용이 인덱스 방식보다 작을 때만 손익분기점이 존재할 수 있습니다. 양쪽 초기 비용 차이가 있을 때 `추가 초기 비용 / 질의당 절감 비용`은 설명용 추정이며 실제 누적 측정과 구분합니다.

같은 질의 반복은 지연 안정성 측정이고, 서로 다른 질의는 업무 반복 비용 측정입니다. 이를 같은 표본 수로 합치지 않습니다. 방식 순서는 균형 있게 섞고 동일 예열 정책을 적용하며 동시 GPU 작업을 피합니다. 표본이 작으면 중앙값·최솟값·최댓값과 개별 값을 보고하고 p95/SLA나 일반적 배수 향상을 주장하지 않습니다.

## 6. 공개 산출물과 결론 형식

원시 JSONL에는 고정 데이터/모델/프롬프트 해시, 질의 ID, 방식, 선택 파일과 이유, 미해결 경로, 호출별 사용량·시간, 실패·fallback, 후보·인용 채점과 제외 이유를 남깁니다. 원문 비밀 값이나 실제 연락처는 넣지 않습니다. 결과 요약에는 세 방식 전체와 실패 실행을 포함하고 재집계 스크립트로 다시 생성할 수 있어야 합니다.

최종 결론은 다음 중 측정 결과에 맞는 형태를 사용합니다.

- 품질 보존 + 비용 절감: 이 저장소·질의·반복 횟수에서 도움이 된 조건과 첫 요청 비용을 함께 제시합니다.
- 토큰 절감 + 시간 증가: 토큰과 latency 결과를 분리합니다.
- 비용 절감 + 누락 증가: 적용 조건을 충족하지 못한 결과로 표시합니다.
- 인덱스만으로 비슷하거나 더 좋음: 코드 인덱스를 기본으로 두고 아키텍처는 구조 설명·검토 보조 용도로 제한합니다.
- 이점 불확실: 필요한 추가 데이터·질의 수와 남은 불확실성을 적습니다.

실험 결과를 보고 질의·예산·그림을 바꾸면 새 protocol 버전으로 기록합니다. 변경 전 결과를 삭제하거나 같은 사전 등록 실험의 성공 결과로 합치지 않습니다.
