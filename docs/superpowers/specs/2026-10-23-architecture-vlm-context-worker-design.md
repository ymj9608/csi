# 아키텍처 다이어그램 VLM 컨텍스트 — 설계 (v2)

> 이 문서는 2026-10-23에 작성된 v1을 대체합니다. v1은 "코드 수정 에이전트(coding_agent)의 수정 범위를 넓혀주는 기능"으로 설계됐으나, 검토 과정에서 "보안/개인정보보호법 위반 판단 자체에는 기여하지 않는다"는 게 드러나 폐기했습니다. v2는 리뷰 단계(`graph.py`)에 맥락을 주는 걸로 범위를 다시 잡았습니다.

## 배경과 의도 (바뀐 부분)

CSI의 정적 분석(Semgrep)은 "비밀번호를 약한 해시로 저장한다" 같은 **코드 패턴**만 봅니다. 같은 패턴이 터져도, 그게 **실제 사용자 개인정보를 다루는 프로덕션 코드**에서 난 건지 **격리된 연습/비프로덕션 코드**에서 난 건지는 전혀 구분하지 못합니다.

실제 Lichu 사례로 보면: `backend/app/core/csi_signup.py`에서 나는 SEC-02(약한 해시)는 "Isolated CSI Lab Mode"(다이어그램에 "Not for production, contains intentional vulnerabilities"라고 명시된 격리 연습 환경)에서 난 거라 실사용자 영향이 없는데, 지금은 이걸 실제 License Catalog/Request Approval(진짜 사용자 데이터 처리) 쪽에서 난 finding과 **똑같은 심각도로 취급**합니다. 리뷰어가 어느 걸 먼저 봐야 할지 판단할 근거가 없는 거죠.

이 기능은 업로드된 아키텍처 다이어그램에서 **"어떤 부분이 격리/연습용이고 어떤 부분이 실제 서비스인지"** 같은 상위 수준 맥락을 VLM으로 읽어서, 리뷰 Agent가 finding을 설명할 때 이 맥락을 참고하게 만듭니다.

## 확정된 결정 사항

- **다이어그램은 프로젝트당 정확히 1장.** 여러 장 합치는 로직 불필요.
- **모델: Qwen3-VL 8B, 로컬 Ollama.** OpenAI 안 씀 — 타겟 고객(아키텍처가 상세한 중소기업/스타트업)엔 충분한 정확도고, 외부 전송 걱정도 없음. (알려진 한계: 멀리 떨어진 연결선 추적은 약함 — 근데 이 기능은 박스 안 설명 텍스트만 읽으면 되므로 큰 문제 안 됨.)
- **VLM 추출은 아주 거칠게(coarse)만 한다.** 박스 이름, 박스에 적힌 역할/설명 텍스트, 격리·프로덕션 여부가 명시돼 있으면 그것, 박스 간 연결 정도. **파일 경로·코드 구조는 VLM이 절대 모르고, 다루지 않는다.** (이유: 그림에 파일 경로가 안 적혀있으면 VLM이 알 방법이 없고, 억지로 추측하게 하면 환각. 사람한테도 파일 경로 입력을 요구하지 않는다 — 그건 "그림이 맞는지 확인"이 아니라 "코드베이스를 다 알아야 답할 수 있는 질문"이 되어 버림.)
- **VLM은 업로드 시점에 딱 1회만 돈다.** 이후 스캔마다 재실행하지 않음 — 저장된 CONFIRMED 결과를 그냥 조회만 함.
- **쓰이는 곳은 `agent/csi_agent/graph.py`(리뷰 단계)다. `coding_agent`는 전혀 안 건드린다.** (v1에서 하려던 "coding_agent 수정 범위 확장"은 폐기.)
- **CONFIRMED 텍스트는 "엄격하게 인용 검증되는 새 근거(fact)"가 아니라, 리뷰 작성 시 참고하는 배경 설명으로 넘긴다.** `analysis.py`의 기존 fact/citation 무결성 검증(인용 안 한 근거 쓰면 에러)을 건드리지 않기 위함.
- **finding과 컴포넌트를 정밀하게 매칭하는 로직을 만들지 않는다.** 확인된 컴포넌트 설명 전체를 매 리뷰마다 배경 정보로 그냥 넘기고, 어떤 부분이 관련 있는지는 리뷰 LLM이 알아서 읽고 판단하게 한다. (컴포넌트 개수가 많지 않은 전제라 비용 문제 없음.)
- **지금 올라와 있는 Lichu 다이어그램은 수정 불필요.** "Isolated... Not for production"과 "Lichu Main Service... license request/approval" 텍스트가 이미 명확해서 이 기능에 필요한 정보가 다 있음.

## 목표

1. 프로젝트 등록 후 다이어그램(1장)을 업로드하면 서버에 저장된다 (현재 IndexedDB만 — 서버 저장 추가 필요).
2. 업로드 시 VLM이 1회 분석해서 "컴포넌트 이름 + 역할/설명 + 격리·프로덕션 여부"를 추출, 각 항목에 OBSERVED/INFERRED/UNKNOWN 태그.
3. 관리자가 콘솔에서 가볍게 확인(✓/✗, 필요시 텍스트 수정)하고 CONFIRMED로 전환.
4. push → 기존 스캔 파이프라인(Semgrep → `graph.py`) 그대로 동작하되, 리뷰(Blue review) 단계에서 CONFIRMED 아키텍처 배경 설명을 추가로 받아, finding 설명에 "이 코드가 격리/연습 환경인지 실제 서비스인지" 같은 맥락을 포함시킨다.
5. 콘솔에서 관리자가 finding을 볼 때, 심각도 숫자는 기존 Semgrep 기준 그대로지만, 설명 문구로 "진짜 급한 것"과 "연습 코드"를 구분할 수 있다.

## 비목표

- `coding_agent` 수정 범위 확장 (v1 아이디어, 폐기 — 보안 판단에 기여 안 함이 확인됨)
- 새로운 아키텍처 위반 탐지 규칙 (예: "이 서비스가 원래 못 거치는 DB에 직접 접속했다" 같은 걸 자동으로 찾아내는 것) — 이건 파일↔컴포넌트 정밀 매핑 + 새 Semgrep류 규칙이 필요한 훨씬 큰 작업이라 지금 범위 밖. 이 기능은 **이미 탐지된 finding의 설명을 보강**할 뿐, 새 finding을 만들어내지 않는다.
- 파일 경로 ↔ 다이어그램 컴포넌트의 정밀 매핑
- 여러 다이어그램 합치기/버전 관리
- OpenAI/Vision API 연동
- Slack 승인, GitHub 자동 PR 생성
- 커밋마다 VLM 재실행

## 구현 계획

| 구성요소 | 위치 | 비고 |
|---|---|---|
| 업로드 → 서버 전송 | `frontend/src/lib/architecture.ts`, `ArchitectureUpload.vue` | 기존 IndexedDB 저장 외에 서버로도 전송. 프로젝트당 1장이므로 "폴더 여러 개" UI는 이 기능엔 불필요(기존 UI 유지하되 서버 업로드는 최신 1장만) |
| 결과 확인 화면 (신규) | 콘솔 새 화면 | 컴포넌트별 이름/역할/상태 카드, OBSERVED/INFERRED/UNKNOWN 뱃지, 가벼운 확인·수정, "전체 확인" → CONFIRMED |
| 저장소 | 새 Flyway migration (V7+) + Controller | 프로젝트당 다이어그램 1장 + 추출 상태(QUEUED/EXTRACTED) + 컴포넌트 목록(JSON) + CONFIRMED 여부 |
| VLM 추출 Worker | 새 top-level 폴더(`architecture_agent/`), `coding_agent/`와 같은 레이아웃 (poll/claim) | Docker 밖, 로컬 Ollama 있는 머신에서 실행. 프롬프트는 "박스 이름/역할/격리 여부/연결 관계"만 추출하도록 제한 — 파일 경로 요청 금지 |
| MCP 도구 | `mcp_servers/business.py`에 추가 (예: `get_confirmed_architecture(scan_id)`) | `get_privacy_policy(scan_id)`와 동일 패턴 — scan_id로 받아 백엔드가 스캔 시점 프로젝트의 CONFIRMED 아키텍처를 스냅샷으로 반환 (나중에 다이어그램을 고쳐도 과거 스캔 리포트 의미 안 바뀜) |
| 리뷰 반영 | `agent/csi_agent/graph.py` / `planner.py` | Blue review 단계에서 새 도구 호출 → 받은 텍스트를 배경 설명으로 프롬프트에 포함 (엄격한 citation 검증 대상 아님) |
| `coding_agent` | 변경 없음 | — |

## 빌더에게 맡기는 것
