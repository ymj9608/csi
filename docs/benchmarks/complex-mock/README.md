# 복잡한 목데이터 비교

후속 실험: [정교하게 다시 그린 설계도와 Qwen3-VL 8B 비교](readable-v2/README.md). 기존/개선 그림과 완벽 인식 가정을 구분합니다. 이 문서 아래의 결과는 기존 Ministral 비전 실험입니다.

공개 프로젝트에서 그림과 코드 매핑이 실패했던 조건을 분리하기 위해, 코드·설정과 일치하는 서비스 식별자가 있는 합성 아키텍처를 만들었습니다. 24개 서비스, 320개 파일, 4,208줄, 150,114바이트입니다. 서비스 간 경계와 업무 종류를 늘린 데이터이며 수십만 줄의 기업 저장소를 재현했다고 표현하지 않습니다.

**실측 결론:** 전체 코드 입력은 63,775토큰·465.32초, 코드 인덱스는 20,185토큰·180.75초였습니다. 비전은 최초 선택을 개선하지 못해 같은 코드 인덱스로 대체됐습니다. 첫 이미지 인식에는 별도로 115.67초가 들었습니다. 모든 방식에서 필요한 원문 근거 또는 맥락이 누락되어, 품질을 유지한 비전 효율 향상으로 결론 내릴 수 없습니다.

- [아키텍처 PNG](architecture.png) · [SVG](architecture.svg): 28개 구성요소, 26개 연결, 6개 업무 영역. 파일 경로·취약점 정답을 표시하지 않습니다.
- [목코드 전체 ZIP](source-code.zip) · [파일 묶음 정보](source-code.json): 측정에 사용한 320개 소스 파일입니다. 채점 정답과 테스트 코드는 포함하지 않습니다.
- [데이터 생성 방법과 행동 검증](DATASET.md): 서로 다른 24개 업무 로직, 전화번호 처리 경로, 문제 4개와 정상 대조 3개.
- [측정 결과](RESULTS.md) · [호출별 원시 로그](measurements.jsonl) · [집계 JSON](summary.json).
- [모델 응답 원문](model-responses.jsonl) · [응답 감사](response-audit.json): 잘못된 인용, 응답 형식 오류, 추가 조회 후에도 남은 요청을 확인할 수 있습니다.
- [고정 프로토콜](protocol.json): 소스·그림·생성기·선별기·실행기의 SHA-256, 동일 과제와 모델 설정, 입력 예산.

## 비교하는 네 방식

| 방식 | 입력 범위 선택 | 확인하려는 점 |
|---|---|---|
| 전체 코드 | manifest 320개 파일을 모두 배치로 전달 | 전체 소스를 모델에 읽히는 비용과 정답 회수 |
| 코드·설정 인덱스 | import·필드·SQL·YAML 서비스/토픽 관계 | 비전 없이 검색만으로 줄일 수 있는 비용 |
| 비전 + 같은 인덱스 | 실제 이미지 추출 결과에서 시작점 주변 흐름을 추가 | 그림의 추가 기여와 인식 실패·누락 |
| 구조 JSON + 같은 인덱스 | 그림을 그린 구조 정보를 텍스트로 전달 | 구조 정보의 가치와 비전 인식 비용·오류의 분리 |

세 선별 방식은 최대 96개 파일·96,000바이트·연결 3단계라는 같은 예산을 사용합니다. 이 한도는 정답을 모두 포함한다는 보장이 아닙니다. 처음 선택한 파일과 모델의 추가 요청으로 읽은 파일을 각각 기록하고, 그림 밖 `legacy_export`도 채점합니다. 전체 코드도 관계가 있는 서비스 파일을 같은 배치에 유지하도록 묶으며, 모든 군에 최대 2회의 추가 근거 조회를 허용합니다.

전체 코드는 한 번의 컨텍스트에 전부 들어가지 않아 8개 최초 배치로 나눕니다. `customer_profile`과 `notification_dispatch`처럼 서비스가 다르면 서로 다른 호출에 들어갈 수 있습니다. 호출 사이의 전체 근거를 자동으로 합치는 별도 모델 단계는 없고, 모델이 정확한 경로를 요청하면 추가 조회합니다. 따라서 비용·품질 차이에는 관련 근거를 같은 호출에 모으는 효과도 포함됩니다.

한 과제를 방식별 1회 실행하며 순서는 전체 → 코드 인덱스 → 비전 → 구조 JSON입니다. 같은 로컬 모델을 예열한 뒤 사용하고 캐시를 강제로 비우지 않습니다. 최초 이미지 해석 비용은 별도 측정하며, 비전 군에서는 저장한 JSON을 실제 파일에서 다시 읽습니다. 애플리케이션의 업로드·DB·HTTP API 지연은 측정하지 않습니다.

## 해석할 때 주의할 점

서비스 ID가 코드 모듈과 일치하도록 작성한 **비전에 유리한 매핑 조건**입니다. 코드 전용 군도 동일한 실제 모듈·설정 정보에 접근하므로 비교군의 경로 검색 기능을 의도적으로 제거하지 않았습니다. 구조 JSON 대조군은 이미지의 원천 정보이고 보안 정답은 아닙니다.

목코드는 공통 서비스 틀, 서비스별 독립 업무 함수, 전화번호 경로를 실제로 호출하는 테스트로 구성됩니다. 24개의 `domain.py` 업무 함수는 단위 검증되지만 전체 API에 통합된 24개 분산 서비스를 실행한 것은 아닙니다. 그림의 서비스 HTTP 연결은 설정에 표현한 설계 관계이고, 실제 네트워크 호출·배포를 검증하지 않았습니다. 그림의 DB 선도 대표적인 저장 관계만 보여줍니다. 모든 저장 접점이나 백그라운드 작업이 이미지에 들어 있다고 가정하지 않습니다.

데이터와 선별기는 함께 개발했습니다. 모델 실행 전에 동작 정답과 검색 결과를 확인했고, 공유 DB를 곧 서비스 호출 관계로 오인한 버그를 수정했습니다. [사전 점검 기록](../../testing/architecture-routing-preflight.json)에 변경을 남겼습니다. 따라서 독립된 미공개 시험 세트나 기업 시스템에 대한 일반 성능 검증이 아닙니다. 모델 호출을 시작한 뒤에는 해당 입력·선별 규칙·정답을 변경하지 않습니다.

입력 토큰 감소, 실행 시간 감소, 위험 후보 발견, 정확한 원문 근거, 필수 파일 회수는 서로 다른 지표입니다. 정답이나 필요한 맥락이 빠지면 품질을 유지한 효율 개선으로 표시하지 않습니다. 이번 실험은 수정안의 근거를 찾는 단계이며, 모델이 만든 패치를 적용하거나 코드 수정 품질을 검증한 실험은 아닙니다.

## 생성과 확인

CSI 루트에서 목 소스를 다시 생성하고 동작 검증을 실행할 수 있습니다. 실제 CSI/Lichu 소스나 서버 데이터는 변경하지 않습니다.

```bash
.venv/bin/python scripts/build_complex_architecture_fixture.py
.venv/bin/python -m pytest tests/test_complex_architecture_fixture.py -q
.venv/bin/python scripts/summarize_complex_architecture.py
```

마지막 명령은 기존 측정 로그를 집계하며 모델을 다시 호출하지 않습니다. 원본 코드 전체는 `.runtime/architecture-benchmark/complex/repository/`, 모델 응답 원문은 `.runtime/architecture-benchmark/complex/run-v1/`에 있습니다. 팀원은 생성기로 같은 소스와 해시를 재현할 수 있습니다.

저장소에 공유하는 `model-responses.jsonl`에는 이 합성 데이터 실험의 모델 응답을 보존합니다. 실측 직후 원본 응답 폴더가 있는 환경에서 `.venv/bin/python scripts/audit_complex_architecture_responses.py`로 감사를 생성한 뒤 집계합니다. 기존 공유 로그를 재집계할 때는 원본 응답 폴더나 모델 실행이 필요하지 않습니다.

실험 실행기를 고정한 뒤 검토에서 발견한 기록 누락도 남깁니다. 후속 조회 응답이 다시 요구한 유효한 파일 경로를 실행기가 대기 목록에 넣지 않는 경우가 있어, 응답 감사에서 별도로 복원합니다. 동결된 측정 호출과 원래 채점은 변경하지 않으며, 해당 요청이 남아 있으면 조회가 모두 완료됐다고 표시하지 않습니다.

소프트웨어 검증 결과와 범위는 [자동화 테스트 기록](../../testing/complex-architecture-validation.json)에 남깁니다. 테스트 통과는 모델의 보안 판단이 옳다는 뜻이 아닙니다.

새 모델 측정에 사용한 명령은 `scripts/benchmark_complex_architecture.py --prepare` 뒤 `scripts/benchmark_complex_architecture.py`입니다. 이미 프로토콜이나 측정 로그가 있으면 덮어쓰지 않고 중단합니다. 새 실행은 별도 작업 복사본에서 기존 결과를 버전별로 보관한 뒤 이미지를 준비하고 진행해야 합니다.
